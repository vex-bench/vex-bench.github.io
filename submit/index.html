01 / WORKFLOW

Package results. Open a PR.

  1. 01

    Package your evaluation

    Include your configuration metadata, exact prompt template, and original outputs for every task and run, including failures. A packaging command in the benchmark repository is planned to produce this format.

  2. 02

    Coordinate your submission

    Discuss original artifact delivery in a website-repository issue first. Prepare the expanded folder under data/uploads/<submitter-id>/<submission-id>/ for the proposed PR format. Reuse your team's submitter folder for later submissions. One PR may include several configuration folders. Maintainers validate and score your results with the official tools from the benchmark repository, then integrate accepted results here.

You provide original results. The benchmark tooling handles validation, parsing, and scoring; this website receives submissions and displays accepted results. Predictions, file inventories, checksums, and scores are generated during processing.

02 / UPLOAD CONTENTS

Three parts per configuration.

Directory structure
data/uploads/
└── redhat/
    └── redhat-2026-10-05-cursor-grok-4.6/
        ├── metadata.json
        ├── prompt.txt
        └── trajectories/  # Retained locally, ignored by Git
            └── <task-id>/<run-id>/
                └── original outputs, logs, or errors

Each folder represents one model/harness configuration. Different models, prompts, harness versions, or execution settings belong in separate folders. Repeated runs share the same configuration.

The parent submitter folder must match metadata.json's submitter.id exactly. Use a stable lowercase team slug such as redhat. Each submission folder must match metadata.json's id.

The repository versions metadata, prompts, and accepted processed results. Original trajectories are required for processing but currently ignored by Git; do not force-add large logs while artifact delivery remains undecided. The downloadable ZIP is a starter. Replace its placeholder prompt and example metadata with your actual experiment.

Include the exact prompt template in prompt.txt, preserving its text and placeholders. Keep additional recorded instructions and per-task expanded prompts with the corresponding run files.

03 / SUBMISSION ID

A readable, unique folder name.

Naming convention
<submitter>-<YYYY-MM-DD>-<harness>-<model>[-<variant>]

redhat-2026-10-05-codex-gpt-5.5
redhat-2026-10-05-codex-gpt-5.5-high
redhat-2026-10-05-claude-claude-sonnet-4.6
  • Use your stable submitter ID and the UTC date the PR is first submitted. If submission_date is set, it must match that date.
  • Use lowercase letters, digits, hyphens, and dots. Keep dots in versions; convert spaces, underscores, slashes, and other separators to hyphens. Start and end with a letter or digit.
  • The folder name must match metadata.json's id exactly and be unique across uploads and accepted submissions.
  • Add a short variant only when needed to distinguish configurations, such as high, custom-prompt, or 2.
  • Keep the ID stable when correcting the same PR. Use a new ID for a separate submission.

The full configuration stays in metadata; parsers do not infer settings from the folder name. Exact model and harness identifiers remain unchanged in metadata.

Keep the submitter prefix in each submission ID so it remains unique when accepted entries are stored outside the submitter folder.

04 / METADATA

Describe the experiment you ran.

This example describes the active Red Hat Cursor / Grok 4.6 configuration. Unknown settings remain unknown. Only final outputs were supplied; full interaction traces are unavailable. Its historical submission date was supplied by the maintainer.

Required fields are schema_version: 1, id, submitter.id, submitter.name, dataset.id, dataset.version, model.id, harness.id, run_ids, artifacts.format, and artifacts.content. Reference an exact published dataset release. Run IDs must be nonempty, unique, and match the original directory names.

Display names, model provider, harness version, model and harness settings, execution settings, access provider, protocol, submission date, and cost_basis are optional. Omit unknown settings or use null; empty settings objects mean nothing was recorded. Record known settings such as reasoning effort, enabled tools, and timeout. Preserve the recorded pricing basis for any cost estimate. Keep access providers such as Vertex AI separate from the harness and model developer.

Use YYYY-MM-DD for the actual submission date, or null if unknown. Never substitute the packaging or build date. A matching dataset alone does not establish protocol equivalence.

Submission IDs, submitter IDs, task IDs, and run IDs must be single path components, with no slashes, backslashes, or . / .. components. Exact model identifiers may include provider prefixes.

05 / ORIGINAL RUN FILES

Keep the original investigation.

Include every task in every declared run exactly once under trajectories/<task-id>/<run-id>/. Use the task IDs from the selected dataset task file, rather than CVE IDs alone. Release 2026-05 contains 75 tasks; Red Hat's three runs produce 225 task/run directories per configuration. This example does not introduce a minimum repeat count.

Preserve original filenames, subdirectories, outputs, and all available logs and tool records. No common trajectory event format is required. The existing ingestion adapters recognize:

  • Codex: harness.id: codex, artifacts.format: codex-jsonl, result.jsonl, and artifacts.content: recorded-events.
  • Claude Code: harness.id: claude (or the legacy vertex_claude_code), artifacts.format: claude-code-jsonl, result.jsonl, and artifacts.content: recorded-events. Record access_provider: "Vertex AI" when applicable.
  • OpenCode: harness.id: opencode, artifacts.format: opencode-session-json, result.json plus available artifacts/, and artifacts.content: session-export-and-logs. Historical mixed exports use artifacts.format: opencode-jsonl-or-session-json; preserve both result.jsonl and result.json when available.
  • Cursor: harness.id: cursor, artifacts.format: cursor-local-isolated-json, result.json containing an output string, and artifacts.content: final-output-only.

Declare final-output-only records explicitly when no interaction trace was supplied. Other harnesses or output formats need a matching parser before scoring; preserve the originals and identify the format in your PR.

Keep failures in the submission.

Retain timeouts, crashes, invalid answers, partial output, and diagnostic logs. Every task/run directory needs at least one result or error/diagnostic file. If none exists, add error.txt with the recorded failure, or No result recorded; cause unknown. when the cause is unknown. The parser determines parsing status.

You do not need to supply predictions, labels, aggregate metrics, checksums, a file inventory, or a batch manifest. Keep raw logged usage when available; unknown usage and cost remain unknown.

Original run files are retained locally for processing. The public trajectory viewer is planned for a future release.

06 / PROCESSED RESULTS

From uploaded files to scored results.

The benchmark tooling produces a separate result package for each submission. Submitters provide the upload files above; maintainers handle these processing outputs.

Processed result package
data/submissions/<submitter-id>/<submission-id>/
├── predictions.jsonl
├── reference_metrics.json
└── processing.json

These files contain per-task/per-run predictions, aggregate scores, and processing provenance. Metadata, the prompt, and original run files stay in the matching upload folder. Prediction references resolve relative to that upload.

A result package's processing.json records its submission ID, upload path, input/output hashes, and source attribution. The website reads these stored results after checking the receipt; it does not rerun parsing or scoring. An upload appears on the leaderboard only when its matching processed package exists.

An active example is redhat-2026-10-05-cursor-grok-4.6: 225 predictions for 75 tasks across three runs. Its outputs were parsed and scored with the benchmark evaluator through a temporary conversion to the legacy staging format; regenerated predictions and metrics matched the saved files byte for byte.

The current leaderboard includes nine paper configurations and four Red Hat Cursor configurations. The four Cursor packages contain 900 task/run records, including four parsing failures, and retain their final-output-only limitation. Paper results preserve their recorded scores across three evaluation runs, numbered 001, 002, and 003.

A fresh checkout includes metadata, prompts, and processed results. Raw trajectories and deferred local archives are excluded from Git and the deployed website. The trajectory viewer and native processing of this upload layout remain pending.
